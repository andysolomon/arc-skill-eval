Major agent tools, including Claude Code, Cursor, Codex, Gemini CLI, Pi, OpenCode, and OpenHands, support the [agentskills.io](https://agentskills.io) format: a `SKILL.md` file plus optional scripts and assets, dropped into a directory that the agent picks up automatically. The format is open, the ecosystem is growing, and skills are easy to write.

They're also easy to ship without testing.

*A note on lineage.* I borrowed most of the methodology in this series almost wholesale from OpenAI's [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills) (Kundel & Chua, January 22, 2026). That includes the layered grader, the advice on growing a case set, and the framing of an eval as a prompt, a captured run, and a small set of checks. Anthropic's published `evals/evals.json` shape gives the methodology a portable on-disk form. The runtime philosophy, *"an LLM, a loop, and enough tokens"*, comes from two posts that demystified the agentic harness: [Thorsten Ball's "How to Build an Agent"](https://ampcode.com/notes/how-to-build-an-agent) and [Mihail Eric's "The Emperor Has No Clothes"](https://www.mihaileric.com/The-Emperor-Has-No-Clothes/). ## The problem: skills ship without tests

A skill is a markdown file. It changes model behavior in ways that are easy to *feel*, as in "this skill helps the model do X better". It is also easy to ship: drop the file in `.claude/skills/` and reload. But almost no skill ships with a way to *prove* the claim. Because skills change model behavior rather than deterministic program output, ordinary code diffs do not reveal behavioral regressions.

A skill that subtly regresses doesn't throw a stack trace. It feels different: vaguer, slower, more verbose, or less reliable on the edge cases the previous version handled cleanly. By the time you notice, you don't know what changed. The diff is a few words in `SKILL.md`. The behavior is several percentage points worse, on cases you can't list.

This is the gap evals fill.

## What an eval actually is

The framing varies by source, but the shape is the same. OpenAI's developers blog defines an eval as **a prompt, a captured run (trace and artifacts), a small set of checks, and a score you can compare over time**. Anthropic's engineering blog adds the formal apparatus. Graders come in three kinds (code-based, model-based, and human), each with its own trade-off between speed and accuracy. Eval suites split into *capability* tests ("does this skill produce the right behavior?") and *regression* tests ("does it *still* produce it after I edited the prompt?").

Both posts reach the same point: evals are the repeatable evidence of how a skill behaves before and after a change. For traditional code, that evidence comes from unit tests, integration tests, and type checkers. For skills, it comes from eval suites.

## Two failure modes evals catch

### Capability: does it ever work?

The capability question is a *pass@k* one. Run the case k times. How often does the skill produce the right behavior?

You don't need 100%. Models are non-deterministic; that's a fact of the medium. What you need is to *know*. If you ship a skill thinking it works 100% of the time and it actually works 70%, you'll find out when a user complains, not when you tested it.

For the hello-world reference skill: does it write `greeting.txt` with the literal string `Hello, world!` and confirm the filename in its reply? Run that case ten times. Nine passes indicate a higher observed success rate than two, for that model and case. The number matters; the answer is empirical.

### Regression: does it still work?

The regression question is a *pass^k* one. It asks whether all k runs succeeded, not whether at least one did. This is what you check after every meaningful edit to `SKILL.md`. A regression in a skill looks like this: the previous version passed nine of ten runs, and the new version passes seven of ten. You can't see that without an eval suite. You can't even *describe* it without one.

Capability evals catch new bugs. Regression evals catch reintroduced bugs. The same case can serve both. What changes is when you run it and what you compare against.

## Why compare with and without the skill

`arc-skill-eval`, like Anthropic's published methodology, reports this comparison as the primary metric. A case that passes 100% of the time *with* the skill attached tells you nothing if it would also pass 100% of the time *without* it. The model would have done the right thing on its own, and the skill contributed nothing.

The signal a skill author wants isn't the absolute pass rate. It's the *delta*: how much does attaching this skill change the outcome?

For hello-world, this is concrete. Run "Create a greeting" against a current Claude or GPT model. With the skill attached, it writes `greeting.txt` containing exactly `Hello, world!` and confirms the filename. Without the skill, with the same prompt, model, and fresh workspace, agents usually write *some* greeting file. But they pick a different filename (`hello.txt`, `world.txt`), use a slightly different format ("Greetings!", "Hello world."), or skip the file and reply in prose. The case's pass rate drops sharply.

That delta is evidence that the skill changed results on the evaluated cases. It separates the skill's contribution from the base model's competence. The OpenAI post mentions baselines; Anthropic's methodology makes them the headline. `arc-skill-eval` makes the delta the central artifact. Every `--compare` run writes a `benchmark.json` whose top-level numbers are the per-case and overall deltas.

If a skill's delta is zero, the skill isn't doing anything. That's not a bug in the eval. It's information. Maybe the model has improved enough that the skill is redundant. Maybe the skill's instructions don't change the result. Either way, you'd want to know.

## A minimum viable eval suite

Don't try for complete coverage. OpenAI's post lands on a useful number: **10 to 20 cases**. Aim for a small set that catches the regressions you care about, and grow it from real failures.

What goes in those cases?

- **Three to five trigger cases.** Does the skill activate when it should? Include one or two "adjacent negative" prompts that look like the skill's domain but ask for something else, so you can confirm the skill *doesn't* fire on them.
- **One to three execution cases.** Does the skill do real work? Back each one with a fixture under `evals/files/` if it needs existing state.
- **One or two edge or negative cases.** Does the skill handle malformed input, ambiguity, or conflict without breaking?

For each case, layer assertions in priority order:

- **Script assertions first.** `file-exists`, `regex-match`, and `json-valid` are cheap and deterministic, and they fail honestly. They cover the mechanical facts: did the file exist, did it contain the right text, did the JSON parse.
- **String assertions for prose.** Use them for what a script can't check. Anthropic's grader prompt requires concrete evidence for a PASS, such as a quoted passage from the assistant's reply or a workspace file. Don't give the benefit of the doubt. If the judge can't cite evidence, the assertion fails.

Budget two to five assertions per case. With more than that, one of them will start failing for the wrong reasons, such as paraphrasing, formatting drift, or a regex that was too strict. A tight, honest set is better than a long, noisy one.

This is also the practical reason to grow your suite from real failures. Every time you debug a regression by hand, you've found a case the suite didn't have. Add it. The next time the same regression appears, the suite will catch it before you do.

## What I built and what's next

`arc-skill-eval`, branded **Skeval** for the docs, is a runner for exactly this loop. You write `evals/evals.json` next to your `SKILL.md` in Anthropic's published format, with no extensions. The CLI finds it, copies any fixtures into a fresh temp workspace, runs each case with the skill attached, grades the output, and writes a tree of artifacts (`assistant.md`, `outputs/`, `grading.json`, `timing.json`, `trace.json`, `tool-summary.json`, `context-manifest.json`) that you can inspect, diff, or feed into CI.

Add `--compare` and every case runs twice, once with the skill attached and once without. The run writes a `benchmark.json` aggregate that answers the question that matters: *does this skill improve results?*

I plan three more posts in this series:

- **Part 2: Anatomy of `evals/evals.json`.** The format end to end: the case shape, assertion families, fixtures and workspace setup, the artifact tree, and the hello-world example as a template.
- **Part 3: Building `arc-skill-eval`, design choices and what I deprecated.** The pivot from a custom TypeScript contract format to Anthropic's published standard. It covers what survived (the Pi runtime, fixture setup, the canonical trace shape), what didn't (lanes, profiles, scorer packs, custom report formats), and why the with/without delta ended up shaping the rest of the design.
- **Part 4: What I learned running it.** Where the methodology is honest, where it only looks rigorous, and where it breaks down: multi-turn skills, stateful agent loops, and skills whose value is hard to pin to one case.

If you want to try it now, the [Quickstart](/arc-skill-eval/quickstart/) gets you to a green run on the bundled `hello-world` skill in about five minutes. The repo is at [github.com/andysolomon/arc-skill-eval](https://github.com/andysolomon/arc-skill-eval).
